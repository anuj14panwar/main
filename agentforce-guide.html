01What is Agentforce

Agentforce is Salesforce's platform for building autonomous AI agents — digital workers that read a customer's natural language message, reason about what they need, pick the right action, execute it against live Salesforce data, and respond. All without a human clicking anything.

The key shift

Flows follow paths you hardcode. Agentforce agents reason. You define the boundaries — the LLM decides which tool to use within them, in real time, based on what the customer actually said.

02Architecture

Every Agentforce agent is made of these layers. Atlas is the reasoning engine that orchestrates everything using a ReAct (Reason + Act) loop.

ChannelExperience Cloud · WhatsApp · Slack · Voice — where the customer talks
↓
Topic SelectorAtlas reads the message and routes to the right Subagent
↓
Subagent (Topic)Scoped area of work — "Loan Status", "Document Check", "EMI Calc"
↓
ActionsApex @InvocableMethod — calls Salesforce data, runs logic, returns output
↓
Atlas ResponseReads action output + instructions → generates natural language reply
↓
Einstein Trust LayerPII masking · Zero data retention with LLM · Full audit log

//The ReAct Loop

Atlas does not call actions randomly. It uses a Reason → Act → Observe loop for every turn:

1
Reason
Reads the message, conversation history, subagent instructions, and available actions. Decides what to do.
2
Act
Calls the selected Apex action with the right parameters extracted from the conversation.
3
Observe
Reads the action's output. Decides if another action is needed or if it has enough to respond.
4
Respond
Generates a natural language reply using the action data + subagent instructions.

//Agent Script — The New Language

Agent Script is a domain-specific language that mixes plain natural language with deterministic programming constructs. It is the most reliable way to control agent behaviour — especially for action chaining.

Agent Scriptloan_application_status subagent
subagent loan_application_status:
    label: "Loan Application Status"
    description: "Use when customer asks about loan status,
                  approval update, or application progress."

    instructions: ->
        | You help customers check their loan application status.
        | Execute actions immediately when inputs are available.
        | Never say you will check — just call the action.

    after_reasoning:
        -- Capture inputs from the conversation
        if @customerEmail != "" and @loanNumber != ""
                and @isVerified == false:
            call verify_customer_identity(
                customerEmail: @customerEmail,
                loanNumber: @loanNumber
            )
            set @isVerified = verify_customer_identity.isVerified
            set @firstName  = verify_customer_identity.firstName
            set @contactId  = verify_customer_identity.contactId

        -- Chain to status action immediately after verification
        if @isVerified == true:
            call get_loan_application_status(
                loanNumber: @loanNumber,
                contactId: @contactId
            )
            | Address customer as @firstName.
            | State status, expected date, officer, branch.
            | Mention pending documents if any.
            | End: "Is there anything else I can help with?"

        if @isVerified == false and @customerEmail != "":
            | "I was unable to verify your details. Please
              double-check your email and loan number."

        if @customerEmail == "" or @loanNumber == "":
            | Ask for whichever value is missing.
Why after_reasoning matters

The after_reasoning block runs deterministically after Atlas reasons — it bypasses the LLM's tendency to narrate instead of act. Use it for any action that must fire immediately when inputs are available.

06Apex Actions

All 5 actions use @InvocableMethod. The description parameter is the most important — Atlas reads it to decide when to call the action.

//Action 1 — VerifyCustomerIdentityAction

ApexVerifyCustomerIdentityAction.cls
public without sharing class VerifyCustomerIdentityAction {

    public class ActionInput {
        @InvocableVariable(label='Customer Email' required=true)
        public String customerEmail;

        @InvocableVariable(label='Loan Application Number' required=true)
        public String loanNumber;
    }

    public class ActionOutput {
        @InvocableVariable(label='Is Verified')       public Boolean isVerified;
        @InvocableVariable(label='First Name')        public String  firstName;
        @InvocableVariable(label='Contact Id')        public String  contactId;
        @InvocableVariable(label='Error Message')     public String  errorMessage;
    }

    @InvocableMethod(
        label='Verify Customer Identity'
        description='Verifies identity by matching email and loan number.
                     Always call first before sharing any data.'
        category='Identity & Security'
    )
    public static List<ActionOutput> verifyIdentity(
            List<ActionInput> inputs) {

        List<ActionOutput> results = new List<ActionOutput>();

        for (ActionInput inp : inputs) {
            ActionOutput out = new ActionOutput();
            try {
                String email   = inp.customerEmail.trim().toLowerCase();
                String loanNum = inp.loanNumber.trim().toUpperCase();

                if (String.isBlank(email) || String.isBlank(loanNum)) {
                    out.isVerified   = false;
                    out.errorMessage = 'Email and loan number are both required.';
                    results.add(out); continue;
                }

                // WITH SYSTEM_MODE bypasses both sharing AND FLS
                // without sharing only bypasses record sharing — NOT field-level security
                // FLS failures on WHERE fields silently return 0 rows — no exception
                List<Contact> contacts = [
                    SELECT Id, FirstName, LastName, Email
                    FROM   Contact
                    WHERE  Email = :email
                    AND    Id IN (
                        SELECT Applicant__c
                        FROM   Loan_Application__c
                        WHERE  Application_Number__c = :loanNum
                        AND    Applicant__c != null
                        WITH   SYSTEM_MODE
                    )
                    WITH   SYSTEM_MODE
                    LIMIT  1
                ];

                if (!contacts.isEmpty()) {
                    Contact c   = contacts[0];
                    out.isVerified  = true;
                    out.firstName   = c.FirstName;
                    out.contactId   = c.Id;
                } else {
                    out.isVerified   = false;
                    out.errorMessage = 'Could not verify identity. Please check your email and application number.';
                }
            } catch (Exception e) {
                out.isVerified   = false;
                out.errorMessage = 'Verification error. Please try again.';
            }
            results.add(out);
        }
        return results;
    }
}

07WITH SYSTEM_MODE — Critical Fix

Production bug — silent data failure

The query was returning zero rows despite correct inputs and without sharing on the class. Debug logs showed the right email and loan number reaching the action. No exception was thrown. Just zero results.

The root cause: Field-Level Security on the Email field of Contact. The Agent Integration User (Einstein Agent User profile) had no FLS access to the Email field. When FLS blocks a field used in a WHERE clause, Salesforce does not throw an error — it silently returns zero rows.

MechanismWhat it controlsBypassed by without sharing?Bypassed by WITH SYSTEM_MODE?
Record sharing rulesWhich records user can see✅ Yes✅ Yes
Organisation-wide defaultsDefault record visibility✅ Yes✅ Yes
Field-level securityWhich fields user can read❌ No✅ Yes
Object permissionsObject access❌ No✅ Yes

//The Fix

Add WITH SYSTEM_MODE to every SOQL statement in all agent action classes. It is applied at the query level — not the class level.

SOQLBefore vs After
// BEFORE — without sharing on class only bypasses record sharing
// FLS on Email field silently returns 0 rows
List<Contact> contacts = [
    SELECT Id, FirstName, Email
    FROM   Contact
    WHERE  Email = :email   // FLS blocks this field → 0 rows, no error
    LIMIT  1
];

// AFTER — WITH SYSTEM_MODE bypasses both FLS and sharing
List<Contact> contacts = [
    SELECT Id, FirstName, Email
    FROM   Contact
    WHERE  Email = :email
    WITH   SYSTEM_MODE   // bypasses FLS → query works correctly
    LIMIT  1
];

// Also needed on inner subqueries
AND Id IN (
    SELECT Applicant__c
    FROM   Loan_Application__c
    WHERE  Application_Number__c = :loanNum
    WITH   SYSTEM_MODE   // required on inner query too
)

No Prompt Templates — by design

Atlas generates responses naturally from action output + subagent instructions. Prompt Templates would add a third LLM call in the chain unnecessarily, add a 5-input limit constraint, and introduce Prompt Builder errors. For this use case they add complexity without value.

11Key Lessons from Building This

Lesson 1

without sharing ≠ bypassing FLS. It only bypasses record-level sharing. Field-Level Security is always enforced. Use WITH SYSTEM_MODE on every SOQL in agent actions.

Lesson 2

The @InvocableMethod description is your routing logic. Atlas reads it to decide when to call the action. Write it in natural language describing the exact user intent that should trigger it — the more specific the better.

Lesson 3

Use after_reasoning in Agent Script for deterministic action chaining. The LLM will narrate instead of act if you leave it to its own reasoning. The after_reasoning block makes action execution code-driven.

Lesson 4

Prompt Templates are optional. Atlas generates natural responses from action output + subagent instructions without a Prompt Template in the middle. They add complexity, a 5-input limit, and Prompt Builder errors for no gain in this architecture.

Lesson 5

Agent Integration User needs the Einstein Agent User profile AND a custom Permission Set. The profile provides system-level Einstein permissions. The Permission Set provides object and field access. Both are required — one alone is not enough.
